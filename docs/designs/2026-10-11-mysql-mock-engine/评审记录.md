### 问题清单

#### P2-1 缺决策：字符串比较/排序、sql_mode、会话时区等「基准语义」未定
- 触发条件：R3/R4 承诺「已声明范围内结果与真实 MySQL 一致」，R1 把 CHARSET 归为「不影响正确性的元数据」。
- 影响：MySQL 默认 collation（utf8mb4_0900_ai_ci / general_ci）决定 `=`、`LIKE`、`ORDER BY`、`GROUP BY`、UNIQUE 的大小写敏感与尾随空格语义；sql_mode 决定 NOT NULL 非严格插入、除零、ONLY_FULL_GROUP_BY；D-08「按会话时区解释」但引擎没有会话时区默认值。这些不定，差分测试（D-09）无法确定基准容器配置，R3/R4 的一致性验收无法断言。
- 证据：决策文件 §2 R1、R3、R4；§3 D-08、D-09 均未提及 collation / sql_mode / 默认时区。
- 建议：新增一条 D：引擎模拟 MySQL 8.0 默认服务端配置（写明 collation、sql_mode、time_zone 的取值），差分基线容器用同一配置；R1 中 CHARSET/COLLATE 改为「解析并用于比较语义」而非忽略。
- 处理状态：待用户决定。

#### P2-2 缺需求与决策：业务代码自身的事务语义（commit/rollback、多连接可见性）
- 触发条件：被测 Service 带 `@Transactional`，测试断言「抛异常后数据回滚」或「REQUIRES_NEW 已提交」。
- 影响：D-06 只决定「不用测试事务回滚做隔离」，没有说引擎支持连接级事务到什么程度。若引擎 autocommit 恒真或 rollback 为空操作，这类测试会得到错误结论；若支持，多连接隔离级别（脏读/串行）又需要取舍。R4/R5 未覆盖。
- 证据：决策文件 §2 R4、R5、R7 与 §3 D-06 均无 commit/rollback/autocommit/隔离级别字样。
- 建议：补 R10（连接级事务可见行为）与一条 D（第一版支持范围：至少单连接 commit/rollback 与 autocommit；多连接可见性选 READ COMMITTED 或全局串行并写明代价）。
- 处理状态：待用户决定。

#### P2-3 规则冲突：F2/R9「影响正确性即显式失败」与 R1「外键仅告警」
- 触发条件：schema.sql 含 FOREIGN KEY，strict 默认开（R9）。
- 影响：外键影响正确性（拒绝孤儿行、级联删改），按 F2 应显式失败；R1 却定为「记录告警、不执行」。两条规则同时成立时实现无所适从，差分测试里违反外键的写入也会出现引擎与真库不一致。
- 证据：决策文件 §2 F2 分支文字、R1 末句、R9。
- 建议：二选一写明：strict 下外键视为不支持特性而失败，或把外键列为 strict 的显式例外并说明依据（如 dine 现网 DDL 不含外键，需第二道核实）。
- 处理状态：待用户决定。

#### P3-1 D-03 与 D-07 对 DML 执行主体的措辞不一致
- D-03：「SELECT/DML 由 Calcite 解析执行」；D-07：「Calcite 只承担查询解析与表达式计算」。DML 由 Calcite 的可修改表执行、还是自有执行器只借 Calcite 算 WHERE，两条读出来不同，影响第二道对实施方案 §3.5 的判读。建议统一为一种说法。

#### P3-2 R8「guava/jackson 窗口内」不可断言
- 窗口区间未定义，Boot 2.1.3 消费方的 guava/jackson 版本也未写。建议写具体区间（D-02 已给 guava 32.1.3-jre 上沿，下沿按 Calcite 1.36 兼容范围）并把「在 Boot 2.1.3 消费方 classpath 下测试通过」作为验收。

#### P3-3 R6「默认拒绝连接真实数据库」不可断言
- 「拒绝」是接管（引擎 DataSource 覆盖应用自带 Bean）还是快速失败（检测到真实 URL 即报错）未定，两者可观测结果不同。建议写明预期行为与可断言结果。

#### P3-4 F6「测试方法结束后恢复」与 D-06「每方法恢复」的时点未统一
- 只在方法后恢复时，前一方法异常中断或 JVM 终止后，下一次运行首个方法的起点不确定。建议改为方法前恢复（或前后各一次），并统一 F6 与 D-06 措辞。

#### P3-5 R3 含 NOW/CURDATE，D-09 未定义差分时钟处理
- 非确定函数在引擎与真库结果必然不同。建议 D-09 后果里写明：固定时钟注入或从差分比较中排除。

#### P3-6 D-02「后果」中的传递依赖版本号属实施事实
- guava/avatica/slf4j 具体版本按归位判据应在实施方案 §2；决策文件只需说「依赖窗口随之固定」。不违反「无路径/类名」规则，轻微。

#### P1-2 现网 DDL 含 STORED 生成列，方案「生成列显式拒绝」使 R1 与 OQ-5 语料不可装载

#### P2-3 Calcite 1.36.0 执行器不支持 UPDATE，D-03「SELECT/DML 由 Calcite 解析执行」不可实现
- 触发条件：按 §3.5「DML 的 WHERE 与表达式计算复用同一 Calcite 计划」并经 Calcite 的 ModifiableTable/TableModify 执行。
- 影响：`EnumerableTableModify.implement` 只处理 INSERT（`INTO`）与 DELETE（`REMOVE_ALL`），其它 Operation 抛 `AssertionError`；DELETE 走 `getModifiableCollection().removeAll` 绕过 §3.4 的 ModificationExecutor，约束与索引不维护。T0「INSERT→UPDATE→DELETE 全链」会在 UPDATE 处失败。`ModifiableTable` Javadoc 明示 "inefficient and experimental"。
- 证据：calcite-1.36.0 `core/.../adapter/enumerable/EnumerableTableModify.java` switch 分支；`schema/ModifiableTable.java` 类注释。
- 建议：D-03 与 D-07 统一为「Calcite 只做解析、校验与表达式/WHERE 求值；INSERT/UPDATE/DELETE 的行变更全部由自有 ModificationExecutor 执行，不使用 Calcite TableModify」；§3.5 写明 UPDATE 的实现路径（例如改写为 SELECT row_id, SET 表达式 FROM t WHERE … 取结果后写回）。第 1 轮 P3-1 升级为本条。
- 处理状态：待用户决定（涉及 D-03 措辞）。
