# MySQL Mock Engine 完整技术方案

技术设计 v1.0 · 面向 Java / Spring Boot / MyBatis · 目标 MySQL 8.0 常用 SQL 子集

## 一、项目定位与总体决策

这个项目建议命名为 mysql-mock-engine。

它的定位不是 SQL Stub 工具，也不是完整 MySQL 数据库，而是：

> 基于 JVM 内存运行、能够直接加载 MySQL DDL、预置数据并执行常见 MySQL SQL 的轻量级数据库模拟引擎，面向 Java 后端业务测试。

典型使用场景是：一个 Spring Boot 服务依赖 MyBatis 访问 MySQL，测试时不启动 MySQL、不启动 Docker、不 Mock Mapper，而是直接执行完整的 Service → Mapper → SQL 调用链，并验证真实计算出来的结果和数据状态变化。

### 技术决策

| 项目                     | 选择                                    |
| ---------------------- | ------------------------------------- |
| 编程语言                   | Java 17+                              |
| 工程构建                   | Maven，多模块                             |
| SQL 查询规划和执行            | Apache Calcite                        |
| MySQL DDL 解析           | Apache ShardingSphere SQL Parser，封装适配 |
| 内存存储                   | 自研轻量 Row Store                        |
| JDBC 接入                | Calcite JDBC 桥接，后续封装自定义 JDBC Driver   |
| Spring Boot 接入         | 独立 Test AutoConfiguration             |
| MyBatis / MyBatis-Plus | 使用标准 DataSource 接入                    |
| 事务                     | 初期单连接基础事务，后续扩展                        |
| 数据隔离                   | 每测试独立实例或共享 Schema + 快照恢复              |
| MySQL TCP 协议           | 第一版不实现                                |
| 生产使用                   | 不支持，严格限定测试用途                          |

这里最重要的架构选择是：复用成熟 SQL 引擎的关系运算能力，自研 MySQL 兼容层和测试数据生命周期管理，而不是重新实现一个完整数据库。

Calcite 已提供自定义表接口、关系查询规划及执行机制，并支持 SELECT 和常见 DML。它的核心模块不包含通用 DDL 执行，DDL 应另行处理。

把系统划分为五个核心领域：

1. Schema：解析并维护 MySQL 表结构。
2. Query：解析、校验、规划并执行查询。
3. Storage：管理行数据和约束。
4. Session：管理连接、事务和会话状态。
5. Testing：管理预置数据、测试隔离和 Spring Boot 生命周期。

其中 Schema 和 Storage 必须由项目自己掌握，不能让 Calcite 内部对象成为业务核心模型，否则后续框架升级或替换执行器会非常困难。

## 三、详细技术设计

### 3.1 MySQL DDL 兼容层

你最关心的是真实项目的 `schema.sql` 能否直接加载，因此应优先解决 DDL，而不是先写一套 Java 建表 DSL。

输入示例：

```
CREATE TABLE `t_order` (
    `id` bigint unsigned NOT NULL AUTO_INCREMENT,
    `user_id` bigint NOT NULL,
    `amount` decimal(18,2) NOT NULL,
    `status` tinyint NOT NULL DEFAULT '0',
    `created_at` datetime(3) NOT NULL,
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_user_id` (`user_id`),
    KEY `idx_created_at` (`created_at`)
) ENGINE=InnoDB
DEFAULT CHARSET=utf8mb4
COMMENT='订单表';
```

建议使用 ShardingSphere 的 MySQL SQL Parser 作为 DDL 解析候选。它提供 MySQL 方言解析和对应语句对象，但具体 DDL 节点覆盖度、AST 信息完整度需要通过真实 DDL 语料验证。

[image](https://www.google.com/s2/favicons?domain=https://shardingsphere.apache.org\&sz=32)

Apache ShardingSphere



DDL 执行流程：

```
CREATE TABLE SQL
       ↓
MySQL DDL Parser
       ↓
DDL Semantic Analyzer
       ↓
TableDefinition
       ↓
SchemaCatalog.register()
       ↓
RowStore.createTable()
       ↓
Calcite Schema 注册
```

核心元数据设计：

```
public record TableDefinition(
    String database,
    String table,
    List<ColumnDefinition> columns,
    List<IndexDefinition> indexes,
    String primaryKey,
    Map<String, String> options
) {}

public record ColumnDefinition(
    String name,
    MysqlType type,
    boolean nullable,
    boolean autoIncrement,
    Object defaultValue,
    boolean unsigned,
    int precision,
    int scale
) {}
```

生产 DDL 中的 `ENGINE`、`CHARSET`、`COLLATE`、`COMMENT` 不应全部直接丢弃。

应该分为三类：

| 类别              | 处理策略                               |
| --------------- | ---------------------------------- |
| 影响执行行为的属性       | 实现或明确拒绝，例如 UNIQUE、UNSIGNED、COLLATE |
| 不影响当前测试结果的元数据   | 接受并保留，例如表注释                        |
| 暂不支持且可能影响正确性的属性 | 启动失败或显式警告，不静默忽略                    |

另外，建议 Schema Catalog 同时支持 `database.table` 的名字解析与配置化大小写行为，避免多数据源、反引号和表名大小写产生隐藏问题。

### 3.2 SQL 查询执行层

这是 Calcite 最值得复用的部分。

例如：

```
SELECT
    u.id,
    SUM(o.amount) AS total_amount
FROM t_user u
LEFT JOIN t_order o ON u.id = o.user_id
WHERE u.status = 1
GROUP BY u.id
HAVING SUM(o.amount) > 100
ORDER BY total_amount DESC
LIMIT 10;
```

内部执行流程：

SQL Parser + Validator

RelNode 逻辑计划

关系运算计划示意

Sort + Limit

Filter (HAVING)

Aggregate (GROUP BY)

Filter (WHERE) + Join

TableScan(t_user)

TableScan(t_order)

Enumerable Executor → QueryResult

为了兼容 MySQL，需要单独建立 `MysqlSqlAdapter`，处理 Calcite 默认 Parser 不能直接接受的语法或语义。

特别需要强调：ShardingSphere AST 和 Calcite AST 不是同一个模型。不建议将所有 SELECT 都先解析为 ShardingSphere AST，再手工转换成 Calcite AST，这相当于额外开发一个 SQL 编译器。

更合适的第一版实现是：

- DDL 走 ShardingSphere Parser。
- SELECT 和常规 DML 优先走 Calcite Parser。
- 对少量 MySQL 特有语法，在 Calcite Parser 扩展或 AST 层处理。
- 对于不支持的 MySQL 语法，明确拒绝执行。

Calcite 的 `MYSQL_5` conformance 只能作为初始配置，不能被视为 MySQL 8.0 兼容证明。

### 3.3 内存存储引擎

第一版不用设计 B+Tree 或复杂的 MVCC。

建议使用行式存储：

```
public final class MemoryTable {

    private final TableDefinition definition;

    private final List<Object[]> rows =
        new ArrayList<>();

    private final Map<Object, Object[]> primaryIndex =
        new HashMap<>();

    private long nextAutoIncrement = 1;
}
```

其中 `List<Object[]>` 是逻辑示意。正式实现应使用行 ID 和受控的行对象，避免数组被外部修改，并保证主键索引、数据行、唯一约束原子更新。

Calcite 可以通过 `ScannableTable` 扫描内存行：

```
public final class MockCalciteTable
        extends AbstractTable
        implements ScannableTable {

    private final MemoryTable storage;

    @Override
    public Enumerable<Object[]> scan(
            DataContext context) {

        return Linq4j.asEnumerable(
            storage.snapshotRows()
        );
    }

    @Override
    public RelDataType getRowType(
            RelDataTypeFactory factory) {

        return MysqlTypeMapper.toRelType(
            storage.definition(), factory
        );
    }
}
```

以上为关键接口示意，`snapshotRows()`、`MysqlTypeMapper` 等需要自己实现。Calcite 官方确实支持通过 `ScannableTable` 暴露 Java 内存行，后续可以再使用 `FilterableTable` 优化过滤下推。

推荐性能策略：先全表扫描，后索引优化。

业务单测往往只需要几十到几千行数据。小数据量下，正确性、启动速度、数据恢复能力比复杂查询优化更重要。

### 3.4 INSERT / UPDATE / DELETE

DML 不只是修改 `List`，必须正确处理：

- 主键与 UNIQUE 冲突。
- `NOT NULL` 与默认值。
- `AUTO_INCREMENT`。
- 影响行数与 Generated Keys。
- UPDATE 同时修改索引列。
- DELETE 后索引一致性。
- 基础事务中的提交与回滚。

建议统一通过 `ModificationExecutor` 执行：

```
public interface ModificationExecutor {

    UpdateResult insert(
        InsertPlan plan,
        SessionContext session
    );

    UpdateResult update(
        UpdatePlan plan,
        SessionContext session
    );

    UpdateResult delete(
        DeletePlan plan,
        SessionContext session
    );
}
```

SELECT 交给 Calcite，UPDATE / DELETE 的筛选条件和表达式仍尽量复用 Calcite 的计划与计算能力，而不是重新编写一个 WHERE 解释器。

Calcite 的 `ModifiableTable` 和 `TableModify` 可以用于 DML 集成，不过官方将 `ModifiableTable` 标为实验性接口。因此建议在自己的执行器接口后面封装它，不让业务代码直接依赖。

[image](https://www.google.com/s2/favicons?domain=https://calcite.apache.org\&sz=32)

Apache Calcite



另外，MySQL 对 UPDATE 影响行数的定义与 Connector/J 的 `CLIENT_FOUND_ROWS` 等配置有关。第一版需要指定并测试默认行为，不能简单把“匹配行数”永远作为“更新行数”。

### 3.5 MySQL 函数和类型兼容

建议建立可扩展函数注册表：

```
public interface MysqlFunctionProvider {

    String name();

    FunctionSignature signature();

    Object evaluate(
        List<Object> arguments,
        EvaluationContext context
    );
}
```

函数执行不要独立于 Calcite 的表达式系统；实际实现应将函数注册到 Calcite 的 Operator Table，并将类型推导和求值实现与之绑定。

第一批支持：

| 类型   | 函数或表达式                                   |
| ---- | ---------------------------------------- |
| NULL | IFNULL、COALESCE、NULLIF                   |
| 条件   | IF、CASE WHEN                             |
| 字符串  | CONCAT、LENGTH、SUBSTRING、TRIM、LOWER、UPPER |
| 数值   | ABS、ROUND、CEIL、FLOOR                     |
| 日期   | NOW、CURDATE、DATE_FORMAT、DATE_ADD         |
| 聚合   | COUNT、SUM、AVG、MIN、MAX                    |
| 比较   | IN、BETWEEN、LIKE、IS NULL、`<=>`            |

数据类型第一版支持：

`BIGINT`、`INT`、`SMALLINT`、`TINYINT`、`DECIMAL`、`VARCHAR`、`CHAR`、`TEXT`、`DATE`、`DATETIME`、`TIMESTAMP`、`BOOLEAN`、`JSON`（以受限功能起步）。

这里建议把 `DECIMAL` 统一映射为 `BigDecimal`，而不是 `double`；日期时间也应保留精度与时区语义，避免测试中的金额和时间行为不一致。

同时要建立明确的 MySQL 兼容性配置，例如：

```
mysql-mock:
  compatibility:
    mysql-version: "8.0"
    sql-mode: "STRICT_TRANS_TABLES"
    collation: utf8mb4_0900_ai_ci
```

这些字段表示期望模拟的行为，不表示实现已经支持该版本或对应排序规则。未实现的配置必须在初始化时给出明确反馈。

## 四、Spring Boot 接入方案

这是整个项目能否真正推广的关键。

我建议同时提供三种接入方式：

| 方式                               | 使用场景                     | 优先级 |
| -------------------------------- | ------------------------ | --- |
| `@MysqlMockTest`                 | 最简单的 Spring Boot 业务测试    | P0  |
| `mysql-mock-spring-boot-starter` | 已有 `@SpringBootTest` 的项目 | P0  |
| `MysqlMock` 原生 Java API          | 不使用 Spring 的单元测试         | P0  |

### 4.1 理想的用户使用方式

测试资源：

```
src/test/
├── java/com/example/
│   └── OrderServiceTest.java
└── resources/
    ├── mysql/
    │   └── schema.sql
    └── datasets/
        └── order-case.yml
```

数据文件：

```
t_user:
  - id: 1
    name: Alex
    status: 1

t_order:
  - id: 101
    user_id: 1
    amount: 100.00
    status: 0
  - id: 102
    user_id: 1
    amount: 200.00
    status: 0
```

测试代码：

```
@MysqlMockTest(
    schema = "classpath:mysql/schema.sql",
    datasets = "classpath:datasets/order-case.yml"
)
class OrderServiceTest {

    @Autowired
    private OrderService orderService;

    @Autowired
    private OrderMapper orderMapper;

    @Test
    void shouldUpdateOrderStatus() {

        orderService.completeOrder(101L);

        Order order = orderMapper.selectById(101L);

        assertEquals(1, order.getStatus());
    }
}
```

这是目标使用 API，并非现成可直接导入的注解。

用户无需显式指定 `DataSource`、创建 H2 表结构或模拟 Mapper。测试启动时自动装载真实 MySQL DDL、预置数据，随后由 MyBatis 对内存引擎执行 SQL。

### 4.2 Spring Boot 自动配置

建议发布独立模块：

```
mysql-mock-spring-boot-autoconfigure
mysql-mock-spring-boot-starter
mysql-mock-junit5
```

配置文件：

```
mysql-mock:
  enabled: true
  schema:
    locations:
      - classpath:mysql/schema.sql
  dataset:
    locations:
      - classpath:datasets/order-case.yml
  reset:
    strategy: SNAPSHOT
  sql:
    strict: true
```

实现自动配置时，不能简单依赖 `@ConditionalOnMissingBean(DataSource.class)`。

原因是：如果应用中已经存在 HikariCP 或自定义 `DataSource`，Mock DataSource 可能不会被创建，最终测试意外连接真实数据库。

我建议区分两种模式：

模式 A：显式接管已有 DataSource

通过测试专用的 `BeanDefinitionRegistryPostProcessor` 或注册阶段的配置机制，替换指定的数据源 Bean 定义。

模式 B：创建 Mock DataSource

对于没有配置真实数据源的测试应用，通过自动配置注册唯一的 `DataSource`。

两种模式都必须显式启用，且默认拒绝连接真实数据库，避免在测试中意外执行 DML。

Spring Boot 自动配置的目标结构可以是：

```
@AutoConfiguration(
    before = DataSourceAutoConfiguration.class
)
@ConditionalOnProperty(
    prefix = "mysql-mock",
    name = "enabled",
    havingValue = "true"
)
public class MysqlMockAutoConfiguration {

    @Bean
    public MysqlMockEngine mysqlMockEngine(
            MysqlMockProperties properties) {

        return MysqlMockEngine.create(properties);
    }

    @Bean
    public DataSource mysqlMockDataSource(
            MysqlMockEngine engine) {

        return new MysqlMockDataSource(engine);
    }
}
```

这是独立 Mock DataSource 模式的简化示意；正式实现还需要处理同名 Bean、多个 DataSource、自动配置排序、SQL 初始化、事务管理器创建以及测试上下文缓存。

为了符合 Spring Boot 的打包规范，应将配置类注册到对应的 `AutoConfiguration.imports` 文件。对于不同 Spring Boot 主版本，应单独建立适配和兼容性测试矩阵。

### 4.3 JDBC 适配是关键基础设施

这里不能只是实现：

```
Connection.createStatement()
```

MyBatis 和 Spring JDBC 还依赖很多 JDBC 特性。

| JDBC 对象           | 必须验证的能力                                  |
| ----------------- | ---------------------------------------- |
| Connection        | autoCommit、commit、rollback、close、isValid |
| PreparedStatement | `?` 参数、setObject、setNull、Batch           |
| Statement         | execute、executeQuery、executeUpdate       |
| ResultSet         | getObject、getLong、getBigDecimal、wasNull  |
| ResultSetMetaData | 列名、别名、类型、精度、可空性                          |
| DatabaseMetaData  | getTables、getColumns、getPrimaryKeys      |
| Generated Keys    | 主键回填                                     |
| SQLException      | SQLState、错误码与异常分类                        |

为了降低初始开发量，第一阶段可以通过 Calcite JDBC 验证 SQL 执行和 MyBatis 基础查询，但正式产品应拥有自己的 JDBC 接入边界，封装元数据和语义差异。

可以提供专用 Driver：

```
jdbc:mysql-mock:mem:order-test
```

或者直接提供：

```
DataSource dataSource =
    MysqlMockDataSource.builder()
        .engine(engine)
        .build();
```

我更推荐 DataSource 作为第一版官方接入接口。它符合 Spring Boot 和 MyBatis 的实际依赖方式，不必为了兼容 `jdbc:mysql://` 而额外实现 TCP 网络服务。

注意：`jdbc:mysql-mock:` 需要自己的 JDBC Driver，不能期望 MySQL Connector/J 自动识别这个 URL。

### 4.4 MyBatis 与 MyBatis-Plus 的适配

核心目标是原有 Mapper 不修改。

```
@Mapper
public interface OrderMapper {

    @Select("""
        SELECT id, user_id, amount
        FROM t_order
        WHERE user_id = #{userId}
        ORDER BY id DESC
        """)
    List<Order> selectByUserId(
        @Param("userId") Long userId
    );
}
```

必须优先验证：

- `#{}` 参数绑定。
- XML 动态 SQL。
- MyBatis `resultMap`。
- MyBatis-Plus `BaseMapper` 的 CRUD。
- `useGeneratedKeys` 及 `keyProperty` 回填。
- MyBatis-Plus 分页插件。
- 逻辑删除和自动填充字段。
- 批量 INSERT / UPDATE。

还要处理 MyBatis-Plus 的数据库类型识别。必要时允许显式配置 MySQL 方言，避免它根据 Mock JDBC URL 识别成未知数据库，但这并不意味着底层 SQL 语义自动变成 MySQL。

### 4.5 测试生命周期与隔离

这是我建议列为 P0 的功能，而不是后续优化。

如果两个测试用例共用内存表：

```
@Test
void testA() {
    mapper.insert(order);
}

@Test
void testB() {
    assertEquals(0, mapper.selectCount(null));
}
```

测试 B 可能受到测试 A 的影响。

建议设计三种隔离模式：

| 模式          | 行为             | 适用范围        |
| ----------- | -------------- | ----------- |
| RECREATE    | 每测试重新建库并装载数据   | 最安全，初期默认    |
| SNAPSHOT    | 初始化一次，每测试从快照恢复 | 默认目标，性能更好   |
| TRANSACTION | 每测试开启事务并回滚     | 适合明确支持的事务场景 |

我建议第一版先实现 `RECREATE`，再加入 `SNAPSHOT`。

快照机制可以采用 Copy-on-Write 或克隆初始数据集。恢复时还必须重置自增 ID、索引、序列和 Session 状态。

不要默认用 Spring `@Transactional` 回滚作为全部测试的隔离方案。 某些业务方法可能使用 `REQUIRES_NEW`、异步执行、独立连接，甚至显式提交事务，测试事务的回滚并不保证覆盖这些写入。

另外，Spring TestContext 会缓存 ApplicationContext。Mock Engine 的生命周期不应该无条件与缓存的 Spring 上下文一一绑定，否则不同测试类可能共享数据库状态。

Spring 官方支持 `@DynamicPropertySource` 和 `DynamicPropertyRegistrar` 等方式将动态测试资源配置注入上下文；这些可以作为特殊场景下的接入机制。

```
    └── spring-boot/
```

模块依赖方向应尽量保持单向：

```
API
 ↑
Schema + Storage
 ↑
Calcite Adapter
 ↑
JDBC
 ↑
Spring Boot / JUnit
```

生产业务测试项目最终只需要依赖 Starter，内部的 Calcite、Parser、Storage 细节都不暴露给使用者。

## 六、开源项目的关键 API 设计

除 Spring Boot 注解接入外，还应该支持不依赖 Spring 的测试。

```
try (MysqlMockEngine mysql = MysqlMockEngine.builder()
        .mysqlVersion("8.0")
        .schema("classpath:mysql/schema.sql")
        .build()) {

    mysql.dataset()
        .table("t_user")
        .row("id", 1L, "name", "Alex", "status", 1)
        .row("id", 2L, "name", "Bob", "status", 0)
        .load();

    QueryResult result = mysql.query("""
        SELECT id, name
        FROM t_user
        WHERE status = ?
        ORDER BY id
        """, 1);

    assertEquals(1, result.rowCount());

    mysql.execute("""
        UPDATE t_user
        SET status = 0
        WHERE id = ?
        """, 1L);
}
```

这同样属于目标 API 设计。

核心接口建议保持简单：

```
public interface MysqlMockEngine extends AutoCloseable {

    void executeDdl(String ddl);

    QueryResult query(String sql, Object... params);

    UpdateResult execute(String sql, Object... params);

    MysqlMockSession openSession();

    void loadDataset(Dataset dataset);

    DatabaseSnapshot snapshot();

    void restore(DatabaseSnapshot snapshot);

    DataSource dataSource();
}
```

单独提供 Session 的目的是让 JDBC 连接、事务状态和引擎状态具有一致的生命周期，而不是所有查询都操作同一个隐式全局事务。

这个项目的质量不能仅靠项目自己的单元测试来衡量。

必须把真实 MySQL 作为行为基准，但只在开发和 CI 的兼容性测试阶段使用。普通使用者执行业务测试不需要 MySQL。

### 建议的兼容性指标

| 指标                   | 第一阶段目标   |
| -------------------- | -------- |
| 目标 DDL 样本解析通过率       | ≥95%     |
| 已声明支持的 SQL 样本结果一致率   | 100%     |
| MyBatis 基础 CRUD 测试   | 全部通过     |
| Spring Boot 基础装载     | 无外部数据库依赖 |
| 普通测试是否启动 Docker      | 否        |
| 未支持特性是否静默执行          | 绝不允许     |
| 测试状态隔离               | 必须通过     |
| Generated Keys 和影响行数 | 覆盖基础路径   |

这里的 95% 是项目规划指标，不是现有测量结果；应先从两三个真实 Java 项目收集 DDL 和 SQL 样本建立基线。

对于结果比较，必须处理一个问题：没有 `ORDER BY` 的查询不能依赖行顺序；但有 `ORDER BY` 时，应该严格比较其规定的排序语义。

## 八、实现路线与里程碑

我建议不要一开始同时开发 SQL 引擎、完整 JDBC、Spring Boot Starter、事务和网络协议。这样依赖关系太复杂，问题很难定位。

阶段 0：技术可行性验证

核心风险消除

用 Calcite 注册两张内存表，执行带 JOIN、GROUP BY、HAVING、ORDER BY 的 SELECT；同时验证从 MySQL DDL 中提取 Schema 能否可靠实现。

交付标准： 直接用真实 MySQL DDL + 预置数据，查询获得与真实 MySQL 一致的结果。

阶段 1：SQL Runtime MVP

实现 Schema Catalog、内存存储、INSERT、UPDATE、DELETE、基础查询、约束和基础函数。

交付标准： 原生 Java API 完成一套订单业务的数据状态变更测试。

阶段 2：JDBC + MyBatis

完成 DataSource、PreparedStatement、ResultSet、元数据、主键回填与事务基础行为。

交付标准： 真实 MyBatis Mapper 不修改 SQL 即可完成 CRUD 和复杂查询。

阶段 3：Spring Boot Starter

实现 `@MysqlMockTest`、自动配置、Schema 装载、Dataset、测试隔离和 Context 生命周期。

交付标准： 已有 Spring Boot + MyBatis 项目只添加测试依赖与注解即可运行。

阶段 4：兼容性与开源发布

扩展 MySQL 函数、异常语义、MyBatis-Plus、并发与快照恢复，建立差异测试报告。

交付标准： 有明确支持范围、兼容矩阵、版本策略和可复现的示例工程。

### 技术风险与应对

| 风险                     | 影响            | 应对                              |
| ---------------------- | ------------- | ------------------------------- |
| MySQL DDL 解析器支持不完整     | 无法导入真实 Schema | 建立 DDL 语料库，先覆盖高频语法              |
| Calcite 与 MySQL 类型语义不同 | SQL 结果错误      | MySQL Type System + 差异测试        |
| Calcite DML 集成复杂       | 写入状态不正确       | 单独封装 DML Adapter，先验证 CRUD       |
| JDBC 元数据兼容不足           | MyBatis 行为异常  | 用真实 Mapper 做端到端验收               |
| Spring 上下文缓存造成数据污染     | 测试随机失败        | Engine 隔离 + Snapshot / Recreate |
| SQL 功能持续膨胀             | 项目失控          | 功能白名单，按真实业务样本扩展                 |
| 自研事务与 MySQL 不一致        | 业务测试误通过       | 明确事务支持级别，复杂事务转真实 MySQL 测试       |

## 九、正式开工前，需要验证的三个技术假设

我认为这三项应该构成项目的最早期 Go / No-Go 判断。

假设 1：Calcite 能承担主要 SELECT 查询。

通过真实项目中约 50～100 条典型 SQL 验证，包括 JOIN、聚合、HAVING、日期函数、分页和动态 SQL 最终生成结果。记录不兼容原因，明确是语法、类型还是执行语义问题。

假设 2：MySQL DDL 能可靠转换为自己的 Schema Catalog。

至少选择包含索引、`UNSIGNED`、`DECIMAL`、`DATETIME`、`AUTO_INCREMENT`、字符集、默认值的真实建表语句进行验证，而不是仅使用演示性的简化 DDL。

假设 3：Calcite 查询计划与自定义可写 Row Store 能一致工作。

必须实际完成 INSERT → SELECT → UPDATE → SELECT → DELETE → SELECT 的全链路，确认约束、主键、自增值和影响行数都能正确反映。不能只证明 Calcite 可以查询 Java List。

如果这三项成立，就可以较有信心地推进 JDBC 和 Spring Boot 层。

## 十、最终推荐的架构决策

坚持纯 JVM 内存执行。

保持开箱即用，不依赖外部基础设施，这是与 Testcontainers 的核心差异。

DDL Parser 与 SQL Query Engine 分离。

避免在 H2 方言上修补真实 MySQL DDL，也避免自研所有查询算子。

Spring Boot 使用 DataSource 替换策略。

不要求用户修改原有 Mapper 或 Service，不把 MySQL Wire Protocol 作为首要开发任务。

测试数据生命周期成为一等能力。

Schema、Dataset、Snapshot、Reset、Isolation 是这个项目真正能够像 `jedis-mock` 一样好用的基础。
