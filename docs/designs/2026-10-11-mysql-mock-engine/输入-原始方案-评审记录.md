## 问题清单

### P1-1 语言基线「Java 17+」与 JDK 8+ 硬约束直接冲突
- 触发条件：任何 JDK 8 消费方（vv-dine-order-service、vv-product-center-service、本仓）在测试 JVM 内加载引擎字节码。
- 影响：UnsupportedClassVersionError，§四 三种接入方式全部失效。三种方式均为进程内嵌入，且第一版明确不实现 MySQL TCP 协议，没有进程隔离的逃生路径。
- 证据：方案 §一 决策表「编程语言 Java 17+」；§3.1 使用 record；§4.4、§六 使用文本块 `"""`；vv-locallife-framework 根 pom.xml 第 10/30 行（spring-boot-starter-parent 2.1.3.RELEASE / java.version 1.8）；dine/AGENTS.md 中两消费服务均为 Java 8 / Spring Boot 2.1.3。
- 建议：source/target 1.8（用新 JDK 编译时走 `--release 8`）；record 改不可变类，文本块改普通字符串拼接；CI 增加 JDK 8 构建矩阵；用 animal-sniffer 拦截误用的 JDK 9+ API。
- 处理状态：未处理。

### P2-1 Calcite 必须钉在 ≤1.36.0，验证版本与升级路径需按此重估
- 触发条件：JDK 8 运行时加载 Calcite。
- 影响：查询引擎冻结在 1.36 线（2023-11），不再接收缺陷修复；§九 假设 1 的 SQL 验证必须在 1.36.0 上执行，新版本行为不能外推；guava 等依赖窗口随之固定，可能加剧与消费方 classpath 的冲突面。
- 证据：Calcite 官方发布记录——1.36.0 声明仍运行于 JDK 7/8（Guava 可低至 14.0），1.37.0（2024-03）起要求 Java 11+。
- 建议：作为显式决策写入方案：接受钉 1.36.0 并写明取舍，或重估引擎选型；假设 1 的 50~100 条 SQL 验证指定在 1.36.0 上跑。
- 处理状态：待决策（对应 D1）。

### P2-2 Spring 接入机制面向 Boot 2.7+/3.x，对 Boot 2.1 主消费基线静默失效
- 触发条件：Boot 2.1.3 消费方使用 starter。
- 影响：`@AutoConfiguration` 注解与 `AutoConfiguration.imports` 注册文件均为 Boot 2.7+ 机制，Boot 2.1 只识别 `META-INF/spring.factories` 的 `EnableAutoConfiguration` 键。按 §4.2 示例实现，自动配置在 Boot 2.1 上静默不加载：`mysql-mock.enabled` 无消费者；若应用自带真实 DataSource 配置，测试将连真实库执行 DML——正中方案 §4.2 自己定义的禁止项。
- 附带：§4.5 引用的 `@DynamicPropertySource`（Spring Framework 5.2.5 引入）与 `DynamicPropertyRegistrar`（Spring Framework 6.2 引入）在 Boot 2.1.3（Spring 5.1.3）均不可用。
- 证据：Spring Boot 官方文档（2.7 引入 @AutoConfiguration 与 .imports 注册，3.0 移除 spring.factories 自动配置注册）；Spring Framework GitHub issue #24540（@DynamicPropertySource）、#32271（DynamicPropertyRegistry bean 化，6.2 落地）；消费基线 pom.xml 第 10 行。
- 建议：兼容矩阵按 Boot 2.1 / 2.7 / 3.x 分列注册机制与可用特性；Boot 2.1 走 spring.factories + 普通 @Configuration（@AutoConfigureBefore 仍可用）；「Boot 2.1 + JDK 8」列为 starter 兼容测试矩阵第一列；动态属性在 Spring 5.1 下用 ApplicationContextInitializer 或直接注册 DataSource Bean 替代。
- 处理状态：未处理。

### P2-3 阶段 0 Go/No-Go 假设未覆盖 JDK 8 这一最大新增不确定性
- 触发条件：按 §九 三项假设推进阶段 0。
- 影响：三项假设即使在默认 JDK 上全部验证通过，仍可能在 JDK 8 上因 Calcite 钉版与传递依赖冲突失败。JDK 8 兼容性是本约束下最高风险项，未进入 Go/No-Go 判定。
- 建议：增加假设 0：在 JDK 8（本机 Zulu 1.8）上，以 Calcite 1.36.0 + ShardingSphere sql-parser 的完整依赖树跑通「真实 DDL + JOIN/GROUP BY 查询 + 写入闭环」，并记录与 Boot 2.1 消费 classpath 的传递依赖冲突清单（guava、antlr 等）。
- 处理状态：未处理。

### P3-1 项目命名前后不一致
§一 建议命名 `mysql-mock-engine`，§五 模块根目录为 `mysql-mock/`。统一其一。

### P3-2 §四 接入方式表三种方式全标 P0，与 §八 里程碑矛盾
里程碑里 `@MysqlMockTest` 在阶段 3 才出现。建议接入优先级对齐里程碑：P0 = 原生 API + DataSource（starter 装载），注解形式列为阶段 3。

### P3-3 junit5 接入在 Boot 2.1 消费方的前提未写明
Boot 2.1 的 spring-boot-starter-test 不带 junit-jupiter，消费方需自行钉 jupiter 版本（本仓已验证 junit-jupiter 5.10.2 + Boot 2.1.3 组合可行，根 pom 第 42-43 行有注释）。建议在 §4 或兼容矩阵中写明该前提，并把该场景纳入 starter 兼容测试。
